## Findings & fixes (all shipped)

### 1. Snakes & Ladders / Ludo accepted junk move payloads — **fixed, live**

`POST /move` with `{roll:99}` / `{token:9}` returned 200: the RNG adapters ignored the payload entirely. Not exploitable (the server rolls and picks the token itself), but validation was sloppy and masked client bugs. Both adapters now return 400 for any non-empty move; race specs still pass.

### 2. `blokus-4p` missing from the API slug allowlist — **fixed, live** (found during the build pass)

Production rejected table creation with 400 because the controller's `IsIn` list lacked the new slug (a wire-up race). Added; live creation verified (`MQKLN7`).

### 3. Hidden-state leak on every move response — **fixed, live** (the serious one)

`PartyService.move()` returned `advanceBots(...)` raw on **three** return paths, bypassing `present()`/`redactFor`. GET views were safe, but every POST /move response carried:

- **Memory Flip:** the full `deck` (all 36 card values) and every bot's `botMemory` — a cheater reading network traffic could play perfectly.
- **Code Race:** the maker's secret `code` while the game was still being raced.

All three sites now redact. Regression spec `party.redaction.spec.ts` locks it in (deck arrives zeroed, botMemory empty, code null while racing). Live probe confirms: deck sum = 0 on move responses.

### 4. Static MP game pages could not create tables at all — **fixed, live** (affects the whole family)

Real-browser testing showed **every** static MP page — including previously shipped ones — failed with `403 Missing or invalid guest token`: the pages invented a bare `guestId` but never obtained the signed token the API guard requires. No human could start an MP table from a game page. New `public/shared/guest.js` mints the `{guestId, token}` pair once per browser via `/guest-users/token` and caches it; all eight game shells await it before their first party call. Browser E2E after deploy: Ludo table created, started, rolled (🎲), bots seated; Snakes & Ladders page creates again too.

### 5. The four newest games had no human-facing presence — **fixed, live**

`ludo-mp`, `checkers-hex`, `checkers-4p`, `blokus-4p` were API-only (backend live, hub-invisible). Shipped family-standard static pages (with client-mirrored legality for checkers jumps and Blokus corner rules, hover preview, pass button, hand/rotation UI), hub registry entries with players tags, and SVG previews. Hub now shows them in the 3P/4P tabs; live counter reads 26 games.

## Product observations (no action taken, reported only)

- **Global throttle is aggressive for shared-IP play:** 100 req/min/IP (guest mint 10/min). My harness hit 429s constantly; a single human game polls ~20–40 req/min and is fine, but two players behind one NAT (café, school) playing simultaneously could see sporadic "Too Many Requests" flash on their dice roll. Consider a small party-endpoint throttle bump or 429-aware retry in `game.js` shells.
- **Memory Flip bot pacing:** bot-only tables take a while (honest memory, no cheating), which is correct but slow — the human-experience timing felt acceptable but is worth a look if players report it.
- **Checkers Hex opening is tight** (only 3 legal first moves because the triangle packs together) — by design, but a heads-up for players expecting many openings.
